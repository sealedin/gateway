# SealedIn gateway

The SealedIn gateway is one OpenAI and Anthropic compatible endpoint to attested open-weight models: an attested gateway plus an enclave identity service, deployed together inside one Intel TDX trust domain. The gateway is a [LiteLLM](https://github.com/BerriAI/litellm) proxy (pinned image, a dependency, not a fork) exposing OpenAI-compatible `/v1/chat/completions` and Anthropic-compatible `/v1/messages` in front of a single upstream, the attested egress (`cmd/egress`), which forwards every request end-to-end encrypted to a Chutes TEE instance whose Intel TDX and NVIDIA GPU attestation verified inside our enclave against a measured policy, so off-the-shelf tooling such as Claude Code connects with a base URL and a bearer key. The identity service (`cmd/identity`) generates an ephemeral Ed25519 key at start and binds its public half into a TDX DCAP quote, which is how clients verify what they are talking to; it also issues the gateway's virtual keys to the operator, so no LiteLLM master key is ever handled outside the enclave.

Production operation requires a real Intel TDX machine: the identity service returns 404 on `/v1/quote` outside a TEE. This README uses [Phala Cloud](https://cloud.phala.com) (a dstack host) as the worked example of a TDX host: the guest agent quotes for the container over a socket. The local docker compose stack is for development only (no TEE, no quotes) and is covered under Local development at the end.

## Deploy the gateway

### Step 1: deploy the enclave on a TDX host

The measured host is Phala Cloud (dstack):

```bash
SEALEDIN_EDGE_DOMAIN=api.sealedin.ai scripts/deploy-phala.sh create sealedin-gateway-01   # first deployment
SEALEDIN_EDGE_DOMAIN=api.sealedin.ai scripts/deploy-phala.sh update <cvm-id>              # roll out a compose change
```

The compose is `docker-compose.phala.yml`. The identity container mounts the guest agent's socket (`/var/run/dstack.sock`) and asks it for the quote with the 64 raw bytes of `REPORT_DATA`; the agent holds the TDX device and the host QGS, so the container runs unprivileged with no device, no vsock and no seccomp change. The guest measures the app compose (compose YAML, env variable names, platform pre-launch script and flags) into RTMR3 as the `compose-hash` event, and `/v1/quote` serves the boot event log next to the quote so a verifier can replay it. Prerequisites: the `phala` CLI (`npm install -g phala`) logged in or `PHALA_CLOUD_API_KEY` set, and the Keychain items below. The env file is encrypted by the CLI to the CVM's KMS key, so only the attested guest reads it; variable names are part of the measurement. The public edge is the custom domain (`SEALEDIN_EDGE_DOMAIN`, `api.sealedin.ai`), routed by SNI through the platform gateway to the edge, whose certificate is ours (issued inside the TD over TLS-ALPN-01 and endorsed by `/v1/tls`). The platform-terminated name `https://<app-id>-8080.<gateway-domain>` also serves the bootstrap and inference under the platform's certificate, never key issuance, and the identity publishes no port of its own. The compose runs three networks: `internal` (`internal: true`, no route out) carries every service but the rpcproxy, only the edge (ACME, inbound), the egress (Chutes) and the rpcproxy (Solana) sit on the routable `egress` network, and `solana` (`internal: true`) joins only the sales service to the rpcproxy, so LiteLLM and Postgres have no path to the internet. The CVM is always-on, with no stop timer; a `tdx.medium` on Phala Cloud costs about 85 to 90 USD a month.

Keychain items: `sealedin-postgres`, `sealedin-chutes` (the Chutes API key the egress attests and invokes with), `sealedin-operator` (the bearer `scripts/issue-key.sh` presents to the identity's key issuance) and `sealedin-solana-rpc` (the Solana RPC provider key the rpcproxy forwards with). The LiteLLM master key is none of them: the identity service derives it inside the CVM from the guest agent's KMS-backed `GetKey` under a fixed path, so it is the same on every boot (the KMS derives per app id and path, so rotating the key means a new version suffix on the path, currently `sealedin/litellm-master/v1`), and hands it through a RAM-only compose volume to the sales service and to the gateway, whose image entrypoint (`gateway/entrypoint.py`) reads it before starting LiteLLM; only the identity mounts the agent socket, the key never appears in an env file and never leaves the enclave. The script materializes a temporary env file from the Keychain via `scripts/env-from-keychain.sh` (the repo's `.env` is never touched); the plaintext exists on disk only for the duration of the CLI call and reaches the CVM encrypted to its KMS key. The guest measures the app compose into RTMR3, so any compose change changes the measurement; that is the point, the workload definition is part of the attested state. Only the dstack guest agent socket is supported as a quote path.

The gateway image is built `FROM` a LiteLLM digest frozen under the policy in [`docs/litellm-pin.md`](docs/litellm-pin.md) (CI fails on any tagged image reference). The compose pins the `gateway-edge`, `gateway-identity`, `gateway-gateway`, `gateway-egress`, `gateway-rpcproxy`, `gateway-sales` and `gateway-drain` images by digest; all seven come from one run of the images workflow (`.github/workflows/images.yml`) on the commit the compose is in, and a new build means re-pinning. Until CI publishes them under `ghcr.io/sealedin`, the compose carries placeholder digests, and `deploy-phala.sh` refuses to run while a placeholder digest remains.

The compose is the release and is identical for every deployment of it, so one release has one compose-hash (the guest hashes the app compose with the `${...}` placeholders intact; the env values are never measured, only their names). The one per-deployment value travels in the env file as a required compose interpolation (`${VAR:?}`, so the stack refuses to start without it): `SEALEDIN_EDGE_DOMAIN`, the custom domain the edge serves (`scripts/deploy-phala.sh` requires it and prints the DNS records the domain needs). It is not attested by RTMR3: the TLS endorsement (`/v1/tls`) proves the certificate a client sees for the domain terminates inside the TD, under the quote-bound key.

The platform's own `*.phala.network` names carry a CAA record that admits only the platform's ACME account, so the edge can hold a certificate only for our domain: [`docs/domain.md`](docs/domain.md) has the three DNS records (an A record to the cluster gateway's address, the `_dstack-app-address` TXT naming the app id and port 443, a required CAA pinning Let's Encrypt, TLS-ALPN-01 and our account), the order of operations from `create` to the CAA record, the checks, the limits (every CVM restart reissues, at most about five a week) and what stays trusted (the registrar and the zone). Key issuance (`/v1/keys`) works only through the custom domain.

The operator's only unmeasured input is the env file (KMS-encrypted operator config): `CHUTES_API_KEY` funds the Chutes account the egress invokes with, next to `SOLANA_RPC_API_KEY`, the fee payer key `SEALEDIN_FEE_PAYER_KEY`, the operator bearer, the database password, the domain and, during the beta, the emergency root key below. Which models exist, which hosts the egress may reach and which TEE measurements it accepts are fixed in the measured gateway and egress images; see the trust model section below.

**Beta root access.** Until the first 10k USD processed, the CVM runs a dstack dev image so an operator can log in and fix it: `deploy-phala.sh` defaults to `dstack-dev-0.5.12`, requires `SEALEDIN_ROOT_SSH_PUBKEY` on a dev image, refuses it on any other, and passes it as `DSTACK_ROOT_PUBLIC_KEY` and `DSTACK_AUTHORIZED_KEYS`, which image versions read differently. Connect with `phala ssh <cvm-name>`. Whoever holds that key can read every prompt, customer key and secret in the CVM. The dev image shows in the quote's guest OS measurements and the variables' names in the measured `allowed_envs`, but the key itself is not measured, so a verifier learns that root login may exist, not whose it is.

**Beta call log.** For launch diagnostics the egress logs one line per upstream call (`egress: upstream call`): model, chute, instance, stream, status, timings and completion tokens, never content, keys, nonces or a client's address or key name. Its exact time and numbers can still be matched against LiteLLM's spend rows, which name a key, so the line is temporary and will be removed. `client_gone` means the egress's caller, LiteLLM, left: `cmd/drain` reads every reply to its end, so an end client hanging up logs the upstream's status.

### Step 2: verify the deployed enclave

```bash
scripts/verify-gateway.sh api.sealedin.ai   # or the platform name <app-id>-443s.<gateway-domain> before DNS exists
```

The script fetches `/v1/quote`, checks that `report_data[32:64]` equals the served pubkey, fetches a second quote with a known `block_id` and checks the identity binds it into `report_data[0:32]`, and checks that the quote is genuinely Intel-signed with an OK TCB (Phala's attestation API today; any DCAP verifier works). Then it ties the quote to the workload: the TD must not be a debug TD, MRTD and RTMR0-2 must equal the pinned guest OS image for the VM shape (`SEALEDIN_EXPECTED_MRS`, see `attestation/`), every RTMR3 event digest is recomputed from its fields (a payload cannot hide under a genuine digest), the digests fold to the quote's RTMR3, the authenticated `compose-hash` event must equal the release's hash (`SEALEDIN_EXPECTED_COMPOSE_HASH`, printed by `deploy-phala.sh`), and the `app-id` event must match the domain. A quote with a matching key but a different compose or guest image fails here.

It then fetches `/v1/tls`, checks the endorsed SPKI against the certificate the public `:443` endpoint actually presents (catching a MITM on a merely CA-valid certificate), requires a Let's Encrypt issuer on the custom domain (the expected app id, cluster gateway and ACME account come from the operator, and `scripts/check-domain-dns.sh` holds DNS to them), and verifies the endorsement signature against the attested pubkey. That check needs OpenSSL 3 for Ed25519 `pkeyutl`, so the script resolves a Homebrew OpenSSL 3 (`/opt/homebrew/opt/openssl@3/bin/openssl`, or the `/usr/local` equivalent) and fails closed with a non-zero exit when none is present; it never skips the check. It also asserts that the private listener's port `:8473` does not answer from the internet, since the compose must never publish it.

A verifying client generalizes the same steps: fetch `/v1/quote` once, pin the enclave pubkey, fetch `/v1/tls`, verify the signature, then pin the endorsed SPKI for its own HTTPS connection (in Go, via `VerifyPeerCertificate`). The pin holds only until the gateway next rotates its certificate, not until `not_after`: Caddy reissues the key at ACME renewal (around day 60), well before expiry (around day 90), so pinning until `not_after` would pin a dead key. When the presented certificate stops matching, re-fetch `/v1/tls` and re-verify rather than fail permanently; `not_after` is advisory.

## Trust model: the endpoint whitelist

The upstream policy is the trust root for provider policy, in two measured layers. The gateway catalog (`gateway/config.yaml`, baked into the gateway image, digest-pinned in `docker-compose.phala.yml`, measured into RTMR3 through the compose-hash) names exactly one `api_base`, the egress on the compose network, mirrored in `internal/gateway.AllowedAPIBases()`, and only Chutes ids flagged confidential, mirrored in `internal/gateway.ConfidentialModels()`; CI fails on anything else. The egress policy (`egress/policy.yaml`, baked into the egress image the same way) pins the Chutes hosts, the re-attestation interval, the accepted TDX measurements (MRTD, RTMR0, RTMR1-3 per guest image, TD attributes, XFAM) and the accepted GPU architectures and confidential modes. Before a request leaves the enclave, the egress has verified the target instance's TDX quote through Intel DCAP with current collateral and TCB status UpToDate, its GPU evidence locally against NVIDIA's device root and through NVIDIA's attestation service against the reference firmware measurements, the binding of the instance's E2EE key into the quote's `REPORT_DATA`, and the measurements against the policy; the request is then encrypted to that key (ML-KEM-768, ChaCha20-Poly1305) and pinned to that instance, so the Chutes balancer and API relay only ciphertext. What this does not prove: which container image and model weights the attested instance loaded, nor that the instance belongs to the chute the catalog named. Two protocol limits are accepted as is: the request is gzipped before encryption, so ciphertext length can leak prompt structure to the relay, and streamed frames carry no sequence, so the relay could drop or reorder middle frames (an early end or a replayed frame ends the reply as a length limit, billed an estimate). sek8s pins the guest OS in RTMR1-3, the signed evidence carries no chute id or image digest, and the chute image is admitted by Chutes' cosign admission controller inside the TD, so the model identity still rests on Chutes' admission and catalog. Changing a host, a measurement, a model or a price means a new image digest and RTMR3, never a per-operator knob. Virtual keys are scoped to the concrete `chutes/` ids; re-issue them with `scripts/issue-key.sh` when the catalog changes, and point clients at those ids.

## Identity service: the quote

`GET /v1/quote?block_id=<hex>` returns `{"quote", "pubkey", "block_id", "report_data_version": 2, "event_log"}` (the boot event log, passed through unparsed, for RTMR3 replay; present whenever the quote is): a base64 DCAP quote whose 64-byte `REPORT_DATA` is `block_id(0:32) ++ pubkey(32:64)`. `block_id` is caller-chosen (hex up to 64 chars, optional `0x`, right-aligned into 32 bytes so short values read as big-endian numbers); the pubkey half never is. Freshness is the verifier's check: it accepts only a value it chose recently, which the requester knows and the enclave need not. With `block_id` set, a fresh quote per request (one at a time; 503 when the quoting slot stays busy past the request budget); without it, the startup quote with zero block id. A verifying client must compare the returned `block_id` and `report_data[0:32]` against what it asked for, and must reject a zero block id when it needs freshness: the zero-id startup quote is public and permanently replayable by design. Outside a TEE the endpoint returns 404. Quoting goes through the dstack guest agent socket (the 64 raw bytes in, quote and event log out); no socket means dev mode, a socket that is present but fails is a startup error.

## TLS endorsement

The quote binds the enclave key but not the transport, so `GET /v1/tls` endorses the gateway's TLS, returning `{"spki_sha256", "not_after", "pubkey", "signature"}`; without it, a host operator with a CA-valid certificate for the VM's domain could terminate TLS outside the trust domain while relaying genuine quotes from inside it. The quote-bound key Ed25519-signs a domain-separated, fixed-width message over the TLS leaf the edge (Caddy) currently presents on the in-TD compose network: ASCII tag `sealedin-tls-endorsement-v1`, one NUL byte, the 32-byte SPKI SHA-256, the not-after as 8 big-endian unix-second bytes. No freshness nonce is needed: the edge TLS key is RAM-only like the enclave key (no cert volume; ACME reissues on every boot), so no past key persists to replay against, and a completed `:443` handshake presenting the endorsed certificate is itself the liveness proof, since only the live in-TD edge holds that key. The endorsement is sound because the identity container dials `edge:443` inside the measured compose topology, so it observes the genuine in-TD certificate. Non-verifying clients keep ordinary WebPKI TLS and stay exposed to that host-operator MITM: the accepted residual risk, closed only by fetching and checking `/v1/tls`.

The plaintext API surface is exactly `/v1/quote` and `/v1/tls`: the self-authenticating bootstrap (payloads Intel-signed and enclave-signed, so the transport adds no trust). The split is enforced in code, not by convention: the public listener (`-listen`, `:8471`) serves only those two routes, while every other endpoint (`/v1/catalog` and `/v1/keys` today, anything later) lives on a separate private listener (`-private-listen`, `:8473`) that the measured compose never publishes, reachable only over the compose network by the edge. The edge itself is a purpose-built image (`edge/Dockerfile`, digest-pinned in the compose and measured like the gateway) whose baked routing table (`edge/Caddyfile`) is an allowlist of exact paths: the bootstrap routes to `identity:8471`, `/v1/catalog` and `/v1/keys` to `identity:8473`, `/v1/keys/buy` and `/v1/keys/recover` to the sales service, the inference routes (`/v1/models`, `/v1/chat/completions`, `/v1/completions`, `/v1/embeddings`, `/v1/messages`, `/v1/messages/count_tokens`, `/v1/responses`) through the drain, and `/key/info` (bearer form only; the `key=` lookup form is refused at the edge) and `/health/liveliness` to the gateway; everything else is a bare 404, so no LiteLLM admin, UI, `/key/generate`, `/spend` or `/config` is reachable from outside, and a raw path with dot segments, encoded or doubled separators is refused before the table is consulted. The platform-terminated `-8080.` listener serves only the self-authenticating routes (`/v1/quote`, `/v1/tls`, `/v1/catalog`) and `/health/liveliness`; inference, `/key/info` and `/v1/keys` are routed only on the end-to-end TLS site (the custom domain), so no client key or operator token ever crosses the platform gateway's TLS termination. The compose cannot bind-mount config, so the table changes only through a new image digest and a new RTMR3.

## Catalog

`GET /v1/catalog` (unauthenticated, behind the edge on both listeners) returns the measured price sheet and payment terms signed by the enclave key: `{models, markup_percent, list_as_of, list_source, pay_to, networks, asset, fee_payer, issued_at, pubkey, signature}`, where `pay_to`, `networks` and `asset` are what a purchase pays and `fee_payer` is absent when purchases are off, where `models` holds one entry per catalog model with `id` (the gateway model id a client requests, `chutes/<upstream id>`), `upstream_id`, `provider` (`chutes`), `tier` (`gpu-tee`), and `input_usd_per_mtok` and `output_usd_per_mtok` as decimal strings in USD per million tokens, sorted by `id`. The prices are exactly those of `gateway/config.yaml` (`internal/gateway.CanonicalModelPrices()`, the Chutes list of `list_as_of` plus `markup_percent`); nothing in the reply comes from a flag or the environment, so a client that verified the catalog for a key knows what every request under that key is metered at.

### Verify the catalog

The signature is Ed25519 under the quote-bound key over this preimage, byte for byte: the ASCII tag `sealedin-catalog-v1`, one NUL byte, then the canonical JSON of the reply with `signature` removed, where canonical means one object with keys in lexicographic order at every level, no whitespace, integers unquoted, prices as strings and only the escapes JSON requires (no HTML escaping of `&`, `<`, `>`). `jq -cjS 'del(.signature)'` on the reply reproduces it, so with the pubkey already pinned from `/v1/quote`:

```bash
curl -sf https://api.sealedin.ai/v1/catalog > catalog.json
{ printf 'sealedin-catalog-v1'; printf '\0'; jq -cjS 'del(.signature)' catalog.json; } > msg.bin
jq -r .signature catalog.json | xxd -r -p > sig.bin
printf '302a300506032b6570032100%s' "$(jq -r .pubkey catalog.json)" | xxd -r -p > pub.der   # must equal the quoted pubkey
openssl pkeyutl -verify -pubin -inkey pub.der -keyform DER -rawin -in msg.bin -sigfile sig.bin
```

`scripts/verify-gateway.sh` runs the same check after the TLS endorsement and prints the signed prices. A verifier must act only on the values it rebuilt from the canonical message it verified, never on fields another parser read from the raw reply: a reply carrying duplicate keys could show one price while the signature covers another.

## Local development

The local compose stack runs the gateway and identity service as sibling containers with no TEE: `/v1/quote` returns 404, nothing is measured, and it exists only to develop against the APIs.

```bash
cp .env.example .env   # set LITELLM_MASTER_KEY; CHUTES_API_KEY only to bring the egress up (the mock model needs none)
docker compose up --build
```

- Gateway: `http://localhost:4000` (OpenAI + Anthropic compatible)
- Identity service: `http://localhost:8471` (bootstrap) and `http://localhost:8473` (catalog, key issuance with `SEALEDIN_OPERATOR_API_KEY` from `.env`)

Connect Claude Code through the gateway:

```bash
export ANTHROPIC_BASE_URL=http://localhost:4000
export ANTHROPIC_AUTH_TOKEN=$LITELLM_MASTER_KEY
```

## Team access

`SEALEDIN_GATEWAY_URL=https://<vm-domain> scripts/issue-key.sh <alias> [max_budget_usd] [rpm_limit]` issues a revocable virtual key with a prepaid USD budget (it never resets) and a rate limit through the identity's `POST /v1/keys`, authenticated with the operator bearer from the Keychain item `sealedin-operator` (`SEALEDIN_OPERATOR_API_KEY` in the sealed env; required in attested mode). The identity calls LiteLLM's `/key/generate` with the master key it derived in the CVM and pins `models` to the measured catalog from `internal/gateway.CatalogModels()`: the request chooses alias, budget and rate limit, nothing else (Claude Code's model picker sees a menu, not a wildcard). The reply is `{"key", "alias", "max_budget_usd", "rpm_limit", "models"}`; `GET /v1/keys/<alias>` (same bearer) returns `{"alias", "spend_usd", "max_budget_usd"}` by exact alias through LiteLLM's `/key/list`. Budget and rate limit are capped by measured ceilings (`internal/keys.MaxBudgetUSD`, `MaxRPMLimit`). No master key is ever presented from outside. Key issuance works only through the custom domain (`docs/domain.md`): the edge routes `/v1/keys` only on its own TLS site, so the operator bearer never crosses the platform-terminated `https://<app-id>-8080.<gateway-domain>` port, and the scripts refuse that name. The operator token is safe to send under two conditions, both enforced: the domain's CAA record pins issuance to our ACME account inside the TD (the platform gateway, which sees every ClientHello, could otherwise pass TLS-ALPN-01 itself and terminate the name; `verify-gateway.sh` refuses a domain without the pin), and the scripts send the bearer only to the server key `/v1/tls` endorsed in a passing `verify-gateway.sh` run (`SEALEDIN_EDGE_SPKI_B64`, pinned with curl's `--pinnedpubkey`), so WebPKI validity alone is never what the token is trusted to.

## Buying a key with USDC

`POST /v1/keys/buy` sells a virtual key, or tops one up, over x402 `exact` on Solana, with a fee payer key the operators hold and can sweep, which pays fees only, receives no USDC, and gives no access to prompts or customers' keys, though its holder can drain its SOL or sign anything else from that address; `POST /v1/keys/recover` gets a key back with a proof from the paying wallet. Both ride only the TLS site, served by `cmd/sales`, the only reader of that key, to which the identity hands the separate secret keys are derived from. Recovery hands back the same key, re-derived, so a payer cannot revoke a leaked one; only the operator can block it. [`docs/x402.md`](docs/x402.md) has the flow, the wire format, what is trusted, the fee payer's funding routine, the limits and recovery. People buy with a Solana Pay transfer instead, claimed at `POST /v1/keys/claim`: [`docs/solana-pay.md`](docs/solana-pay.md).

## Streams and billing

LiteLLM bills a stream only at its end, so inference goes through `cmd/drain`, which reads every reply to its end whatever the client does; [`docs/x402.md`](docs/x402.md#billing-a-stream) has the details. A client that hangs up pays for the whole reply.

## Usage accounting

LiteLLM records one spend-log row per request and a cumulative USD counter per virtual key in the gateway's Postgres (inside the TDX domain, data on the VM's LUKS-encrypted disk). USD amounts come from a measured price sheet: one price per canonical model regardless of provider, the Chutes list price (`gateway/chutes-prices.yaml`, USD per million tokens with its date and source) plus a 5 percent markup, written as literals in `gateway/config.yaml`, mirrored in `internal/gateway.CanonicalModelPrices()` and recomputed by CI with exact integer arithmetic so neither the list nor the markup can drift from the config; `LITELLM_LOCAL_MODEL_COST_MAP` in the compose pins LiteLLM's bundled fallback map to the image copy, so no price depends on an unmeasured input. Changing a price is a governance change (new image digest, new RTMR3). `SEALEDIN_GATEWAY_URL=https://<vm-domain> scripts/usage-report.sh <alias>` prints one key's lifetime spend and budget through `GET /v1/keys/<alias>` with the operator bearer.
