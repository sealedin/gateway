# Buying a key with USDC

`POST /v1/keys/buy` sells a virtual key for USDC on Solana in one request and its retry, following the x402 specs [`schemes/exact/scheme_exact_svm.md`](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact_svm.md) and [`transports-v2/http.md`](https://github.com/x402-foundation/x402/blob/main/specs/transports-v2/http.md). The enclave is the sponsor: it pays the network fee and needs no facilitator. Credits are USD 1:1 with the USDC paid. Both routes ride only the custom domain's TLS site, never the platform-terminated `:8080`, because their replies carry a key. They are served by `cmd/sales`, not the identity, so the process holding the quote-bound key neither parses client transactions nor links the Solana library.

The official x402 Go SDK is not used: it has only pseudo-versions, a closure of about 30 modules and pins an old Solana library, and the scheme's Path 1 is short. That assessment comes from a partial read of the SDK.

## Flow

1. The client posts `{"amount_usd": <number>}`, from 20 to 500 inclusive with at most six decimals.
2. Without a `PAYMENT-SIGNATURE` header the reply is a 402 with `PAYMENT-REQUIRED`.
3. The client builds a version 0 transaction, signs it as payer and leaves the fee payer's signature empty, then repeats the request with `PAYMENT-SIGNATURE`.
4. The sales service verifies the transaction statically, refuses a duplicate, simulates it, co-signs and sends it, and waits until it is confirmed on both RPC hosts.
5. Only then it issues the key, under the alias `x402-` plus 32 hex characters of the SHA-256 of the transaction's message, and replies with `PAYMENT-RESPONSE` and the key. The sponsor's deterministic signature makes a message one transaction, and a digest can be checked before anything is signed. The key's value is derived by HKDF from the enclave-only secret and that digest: the pinned LiteLLM upserts on the token with an empty update, so a late or repeated issuance leaves one row and one budget even where its alias check, which is check-then-create, could not stop it.

With `Authorization: Bearer <existing key>` the same request adds the amount to that key's budget instead. A bad or blocked key gets a 401 before anything is paid, and the reply carries no `key` field.

Before paying, a client should compare the challenge with the signed catalog: `pay_to`, `asset`, `networks` and `fee_payer` in `GET /v1/catalog` are signed by the quote-bound key.

## Wire format

The challenge, base64-decoded from `PAYMENT-REQUIRED`:

```json
{
  "x402Version": 2,
  "error": "PAYMENT-SIGNATURE header is required",
  "resource": {"url": "https://api.sealedin.ai/v1/keys/buy", "description": "A virtual key with credits", "mimeType": "application/json"},
  "accepts": [{
    "scheme": "exact",
    "network": "solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp",
    "amount": "25000000",
    "asset": "EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v",
    "payTo": "<treasury>",
    "maxTimeoutSeconds": 60,
    "extra": {"feePayer": "<fee payer>", "recentBlockhash": "<hash>", "lastValidBlockHeight": "<height>"}
  }]
}
```

The blockhash is a hint, cached for 10 seconds and absent when the RPC host is down; a client then fetches its own. The payment, base64-encoded into `PAYMENT-SIGNATURE`, echoes the terms and carries the transaction:

```json
{"x402Version": 2, "resource": {"url": "https://api.sealedin.ai/v1/keys/buy"}, "accepted": {"scheme": "exact", "...": "as above"}, "payload": {"transaction": "<base64>"}}
```

The transaction must have this static layout, Path 1 of the scheme: compute unit limit, compute unit price, the SPL token program's `TransferChecked` of exactly the amount from the client's account to the treasury's associated token account, then up to four optional Lighthouse or Memo instructions (the last slot Memo only), with at least one non-empty Memo. Fee payer first, client second, no other signer.

The success reply:

```json
{"key": "sk-...", "alias": "x402-...", "max_budget_usd": 25, "rpm_limit": 60, "models": ["chutes/..."], "transaction": "<signature>"}
```

| Status | Meaning |
|--------|---------|
| 200 | Settled and credited, with `PAYMENT-RESPONSE` |
| 400 | Bad amount, a malformed payment header or transaction, or a malformed recovery request |
| 401 | A top-up's bearer is unknown or blocked, or a recovery proof does not verify |
| 402 | No payment yet, or a refused one: `PAYMENT-RESPONSE.errorReason` names it. `settlement_pending` means the transaction left and may still land, so no new challenge comes with it; recovery picks it up once it is confirmed on both hosts |
| 404 | Recovery only: the transaction is not on chain at confirmed commitment |
| 409 | The transaction is settled or in flight, or a recovery could not stand; no key. `PAYMENT-RESPONSE.transaction` is empty until the transaction has left, its id being the sponsor's signature until then |
| 429 | Too many attempts |
| 502 | Settled, but the key could not be issued: `PAYMENT-RESPONSE.success` is true and the body names the transaction; recover it. Without that header, a top-up's bearer could not be checked and nothing happened |
| 413 | The body is too large |
| 503 | Settlement unavailable or the fee ceiling reached, or on recovery the chain cannot be read; nothing was charged |

## Walk-through with curl

```bash
curl -si https://api.sealedin.ai/v1/keys/buy -d '{"amount_usd":25}' | grep -i '^payment-required' | cut -d' ' -f2 | tr -d '\r' | base64 -d | jq .
curl -s https://api.sealedin.ai/v1/catalog | jq '{pay_to, asset, networks, fee_payer}'    # verify the signature as the README shows, then compare
```

Building and signing the transaction takes a wallet library: `internal/x402/x402client` is a short worked example. `scripts/x402-devnet-smoke.sh` runs the whole flow against devnet with local binaries.

## What is checked

Before anything is signed, and failing closed: size at most 1232 bytes, a canonical version 0 encoding, no address lookup table, exactly the fee payer and one client as signers, no account listed twice, the fee payer named by no instruction, at most 400,000 compute units at 5,000,000 microlamports each, one `TransferChecked` of the USDC mint with 6 decimals to the treasury's token account under the classic token program with the client as authority, an amount exactly equal to the request (the scheme tolerates overpayment, this sponsor does not), a memo and a valid client signature. The terms the client says it accepted must match too. Then simulation. Smart wallets, splits, version 1 messages and sponsored account creation are not accepted.

The sponsor's signature is computed only after simulation passed, or when the transaction's id is already public: it is the id, and holding it is holding a broadcastable transaction. Until then everything works on the digest of the message.

## Front-running and duplicates

Once sent, a transaction's bytes are public, so they never grant anything by themselves. A repeated purchase gets a 409 whoever sends it and with whatever bearer, through three independent checks: an in-process claim for the transaction, a key under its alias at the gateway, and the chain knowing the signature at any commitment. A narrow race remains only if the process crashes while the transaction lands and an attacker presents its bytes before the node reports them. A repeat of a settled transaction whose key is gone and whose blockhash has expired fails simulation with a 402 rather than a 409, since the status check names the signature and so waits for a passed simulation; it still gets no key.

A transaction that landed failed has cost the fee payer a fee, so its wallet and its source token account are refused for a day (in process).

## Recovery

`POST /v1/keys/recover` takes `{"transaction": "<base58 signature>", "payer": "<base58 address>", "timestamp": <unix seconds>, "signature": "<base58 Ed25519 signature>"}`. The payer's wallet signs the tag `sealedin-key-recover-v1`, one NUL, the 64 raw bytes of the transaction signature and the timestamp as 8 big-endian bytes. The timestamp must be within two minutes of now, and a proof works once. The proof is checked first, against the declared payer, at no cost; only then does the route read the chain, requiring a confirmed success, this sponsor's own signature, the whole policy, confirmation on the second host, and that the declared payer is the transaction's. Then:

- No key under the alias: it issues one, the crash between settlement and issuance, if the transaction landed within the last 7 days; anything older is a 409 and the operator's to reconcile, or a lost database or a deleted key would reissue every payment. So revocation means blocking a key, never deleting it, and a key blocked under its live alias stays revoked: recovery answers 409.
- A key exists: it hands back the same key, re-derived; a key blocked by the operator stays revoked (409). There is deliberately no rotation, since a rotated key could forgive spend LiteLLM has not booked yet. **So a payer cannot revoke a leaked key**, and anyone holding the wallet can read the key again; only the operator can block it.
- The transaction was a top-up: it finishes the credit if needed and returns the amount credited, never the key or its budget, since the payer of a top-up need not be its holder. A top-up leaves a blocked, zero-budget marker key under the transaction's alias, and the credit is recorded in the target's metadata in the same update as the budget, so it applies once. A crash before the marker means recovery issues a new key for the amount instead. If the target has since been deleted, nothing can tell whether it was credited: the reply is a 409, the log says so, and the payment stays uncredited until the operator reconciles it by hand. That is accepted during the test phase.

The derivation uses a secret the KMS derives per app id and path, `sealedin/virtual-key/v1`, which reaches only the sales service. A new image or compose on the same app id keeps it, and a new app id or a new path version changes it, after which no key on record can be handed back: recovery answers 409 and issues nothing.

Changing the fee payer key changes neither the secret nor the alias, so what was issued stays recoverable: a transaction naming another fee payer gets the same key back, and a top-up marked under it finishes once. **What a change strands** is a payment with no row yet, the crash between settlement and issuance: a transaction under a former fee payer with no key on record is a 409 for the operator to reconcile, because anyone can pay a fee and nothing would show this enclave handled it. So change the key only when no purchase is in flight. Those payments need the operator, as does anything recovery refuses.

## Billing a stream

The pinned LiteLLM books spend only when it reaches the end of a stream. Executed against it: a client that read 5 of 63 chunks and hung up was billed 0 of 2 USD, and the upstream was cut with it. So `cmd/drain` sits between the edge and the inference routes and reads every reply to its end whatever the client does: a client that hangs up, or whose write blocks for 30 seconds, just stops getting its copy, and the request is billed in full. It is bounded by the egress's 10-minute call limit plus a minute, so the egress gives up first. It holds no key beyond the hash of a running request's credential, links no third-party module, has no route out and logs no content, and it sees every prompt and reply passing through, which is why it is that small. The edge and the drain refuse a body over 32 MiB, which LiteLLM would read into memory before checking a key, and since any `sk-` value passes the per-key count, the drain also holds all running requests to 512 MiB of bodies together, a judgment for a 4 GB machine, answering 429 with `Retry-After` past it. A body of unknown length counts as 32 MiB, and a reservation lasts as long as its request. An upload slower than 60 seconds gets a 502. On a stop it waits 25 seconds for LiteLLM's spend flush, or what finished last would go unbilled. `scripts/e2e/stream-billing.sh` (`make e2e-stream-billing`, in CI) runs this against the pinned image, with the pinned Caddy in front for one case.

So a client that hangs up pays for the whole reply, by design, and a live client whose single write blocks for 30 seconds loses the tail and pays too. A client still reading past the egress's 10 minutes also stops getting its copy, or a reader just fast enough to avoid the stall limit could hold LiteLLM back until the cut and pay nothing. Every key may run 10 requests at once, `internal/limits`, a judgment: LiteLLM's `max_parallel_requests` holds only for its 60-second window, so the drain counts per key for as long as a request runs and answers 429 past it. Only `Authorization: Bearer sk-...` or `x-api-key` is accepted there, the bearer winning when both come, as Claude Code can send, and it forwards just that, since LiteLLM authenticates from whichever of several headers it finds first and a junk second one would otherwise be a fresh count.

**What reaches the upstream.** LiteLLM forwards fields it does not price: `extra_body` can set `model` or `stream` behind its back, so a client could pay for a cheap model and get a dear one, or get a whole reply back in an error body for nothing, and a client's own `additional_drop_params` switches off any configured drop. No setting holds this, so `gateway/request_guard.py`, a pre-call hook, removes every field a client sent outside its list. It is the only code of ours inside LiteLLM, and `make e2e-stream-billing` fails if the hook stops being invoked: a smuggled field reaches the fake upstream, which answers 418. The egress refuses `n` above 1, which would multiply output against one reservation, reads the exact keys the upstream reads, and asks for only the final usage chunk.

**What meters.** `disable_token_counter` is on: with it off, LiteLLM counted tokens in the auth path on its one event loop, and a key holder's single prompt of 1 MiB of one repeated character held it for minutes, every other request and its health check with it (a stack dump shows `tiktoken` under `_reserve_budget_after_common_checks`; an invalid key is refused before it, in 0.4 s). Now the same prompt takes 0.4 s and the upstream's usage chunk is all that bills, so the egress guarantees one: a stream that ends without usage, by a failed frame, an upstream end or the 10-minute limit, is closed as a `finish_reason: length` reply with usage estimated at 4 characters a token from the request and from what was delivered. A client can tell it was cut from that finish reason. An estimate can be off in either direction. A non-streaming reply that fails delivers nothing and bills nothing. `/v1/messages/count_tokens` and `/utils/token_counter` answer 503 as a result.

**Budget overrun.** LiteLLM alone does not hold a budget: with its counter off it reserves no input, and it admits a request over the remainder. So `gateway/request_guard.py` refuses a request unless the key can pay its worst case on top of what its running requests may still cost, answering 400 `budget_exceeded`. The worst case is at most one token per byte of the body, which no tokenizer exceeds, capped at the model's context, plus the output as the egress clamps it: the lowest figure named, 16,384 if none, at most the model's `max_output_tokens`, each at the model's price. No tokenizer runs, and a running request counts until 20 seconds after its end, by when its spend shows. The limits are `max_output_length` and `context_length` in the Chutes catalog, recorded with their date in `gateway/chutes-prices.yaml`.

**What is left over.** Ten full-context Kimi-K3 requests naming one output token on a nearly spent key used to be able to cost 10 x 1,048,576 x 1.85e-6 = 19.40 USD of input past the budget. With 1 USD left none is admitted now, and with 5 USD left two are, whose worst case of 1.94 USD each fits (`gateway/request_guard_test.py`, and the end-to-end test). The worst-case overrun is therefore 0 USD, on these conditions, which nothing here can check: the upstream refuses or truncates past its context, counts reasoning inside `max_tokens`, reports honest usage, and charges no image more tokens than its bytes, which a short image link could if a model accepted one. If usage were to arrive more than 20 seconds after a request ended, the difference is one request's worst case, 1.94 + 0.62 = 2.56 USD on Kimi-K3 at most. A restart forgets the count, and the streams it counted die with it.

**Near the end of a balance a request can be refused that would have fitted.** The estimate is deliberately high, about four times real input for English text. A 400 KB prompt naming 32,000 output tokens on Kimi-K3 counts 400,000 x 1.85e-6 + 32,000 x 9.5e-6 = 1.04 USD and may really cost about 0.24 USD, so it is refused once less than 1.04 USD is left, or sooner with others running. The credits are not lost: a smaller prompt, a smaller `max_tokens`, a cheaper model or waiting for running requests all get through, and a top-up adds to the same key.

**Egress slots.** The egress holds 64 requests at once for all keys, and 7 keys at 10 each can hold every slot for up to 10 minutes a call; everyone else then gets a 503. Accepted during the test. Each such refusal logs `egress: at capacity` at error level: that is the alert to watch.

## What is trusted

- **RPC hosts.** The primary provider sees every transaction and can censor or delay them, which costs availability and no money beyond fees. To mint a key without payment it would have to lie about confirmation, and the second, independent host must then lie as well, which is why a confirmation must hold on both. Recovery additionally requires the named fee payer's own signature on what the host returns, and issues nothing new under any but the current one. Two colluding hosts could still issue a key for a transaction that never landed, up to the amount of a transaction a client got signed; with the operators holding the fee payer key, that adds nothing to the key issuance their bearer already allows. Issuance waits for `confirmed`, not `finalized`: a confirmed block rolling back is the residual risk, accepted for speed.
- **LiteLLM.** Its token primary key makes a second issuance for a transaction impossible, and it enforces the budget.
- **The sales service.** It holds the fee payer key, the secret behind sold keys and the LiteLLM master key, as LiteLLM itself does the latter. It has no agent socket and no enclave key, and links the Solana library's dependency closure, which is why it is not the identity.
- **The second confirmation host.** It is the free public endpoint. If it rate-limits this CVM, purchases that did settle end in `settlement_pending` and recovery stalls until it clears; no key is issued meanwhile and nothing is lost. Those replies log at error level: that is the alert to watch.
- **The client's own view.** A client that does not check the challenge against the signed catalog trusts the TLS session alone.

## Fee payer funding

The operators hold this key. `scripts/new-fee-payer.sh` generates it on their machine, stores it in the Keychain item `sealedin-fee-payer` and prints only the address; `scripts/env-from-keychain.sh` passes it in as `SEALEDIN_FEE_PAYER_KEY`, part of the KMS-encrypted sealed env, read by `cmd/sales` alone (`scripts/check-isolation.sh`, and a test of the compose) and dropped from its environment once read. An attested service without a valid key refuses to start. The item's value is the base58 keypair any Solana wallet imports, which is how the operators recover SOL. The address is in the signed catalog, published to the identity by the sales service, and in the startup log. It must hold SOL before the first purchase and be watched afterwards: read `fee_payer` from the catalog, check its balance with `solana balance <address>`, and send SOL when it runs low. An unfunded fee payer shows as an error in the log and 503s to clients, with nothing charged.

What holding it means, as checked against the code:

- **It pays fees and receives no USDC.** The enclave signs only a transaction whose single token transfer goes from the client to the treasury's account, and the policy refuses one naming the fee payer in any instruction. A stranger could still send tokens to this address; nothing here does.
- **It can do anything else its holder signs.** An operator can drain its SOL or sign unrelated transactions from the address. Purchases then answer 503 until it is funded again.
- **It reaches no prompt and no customer key.** Sold keys derive from the separate secret above, TLS and the quote use their own keys, and a test shows sold keys do not change with the fee payer key.
- **It cannot make a payment that did not happen.** Issuance reads the chain for a successful transfer to the treasury. Signing a transaction that pays nothing fails the policy, and signing one that really pays is paying. Only together with two lying RPC hosts could it fake one, and the operators' bearer issues keys anyway. So this adds nothing against the operators, and a key's budget was never a defence against them.

Changing the key: fund the new address, generate the new item, deploy, and sweep the old address with the wallet. See [Recovery](#recovery) for what a change strands.

The treasury's USDC associated token account must already exist: sponsored account creation is not offered, and a transfer to a missing account fails simulation. Keeping the Chutes account funded for the credits sold is the operator's job; there is deliberately no global cap on issued credits.

## Limits

- 20 to 500 USD per purchase. Per-day limits are not enforced by this endpoint.
- No ceiling on a key's total budget through top-ups.
- Attempts: a global bucket of 10, refilled at one every 2 seconds, one for settlements and one for recoveries carrying a valid proof. They are global because the platform gateway passes TLS through without the client's address, so the edge cannot tell clients apart. A flood of well-formed transactions can therefore delay honest buyers.
- Fees: at most 1,005,000,000 lamports per UTC day, 500 settlements at the 2,010,000-lamport worst case. Fees not yet known to have bought a confirmed payment may hold only a fifth of that, 201,000,000 lamports; past it new wallets get a 503, and a wallet with a settled purchase behind it goes on. These figures are derived from the caps, not measured on chain, and the counts are in process, so a restart zeroes them.
- One unresolved transaction per wallet and per source token account, proven or not, or a 402. About three minutes after a transaction is left pending, it is looked at again: dropped on both hosts gets its fee back and frees the wallet, landed resolves, failed keeps the fee and bars the wallet and the source for a day. Simulation checks funds only at that moment, so stopping new buyers takes one funded source at a time, moved on between attempts, plus a new wallet and token account per slot; the money at risk stays bounded by the fifth. If the primary cannot answer, the fee stays booked until the next UTC day. The Path 1 price cap stays at the spec's default: lowering it would cut this cost, but no measurement says which wallets would then fail to land.
- Anyone with a throwaway keypair can make a self-consistent recovery proof for any transaction id, so the recovery bucket can be drained, which delays recoveries and nothing else.
- No browser support: no CORS headers, as the transport spec allows.

## RPC path

Neither the identity nor the sales service has a route out. `cmd/rpcproxy` sits on the routable `egress` network and on `solana`, an internal network only the sales service shares, because its params reach external hosts and LiteLLM must have no way out through it. It forwards only `getLatestBlockhash`, `simulateTransaction`, `sendTransaction`, `getSignatureStatuses`, `getTransaction` and `getSignaturesForAddress` to the primary, and only `getSignatureStatuses` to the confirmation host. Both hosts are in `rpcproxy/policy.yaml`, measured with the image. The provider's API key is the sealed env's `SOLANA_RPC_API_KEY` from the Keychain item `sealedin-solana-rpc`, and it is never logged. `scripts/check-isolation.sh` keeps the proxy away from every signing key. `internal/solanarpc` stays on the stdlib: solana-go's `rpc` package would add modules for these five calls and caps no reply size.

## Before the first deployment

`scripts/check-release-pins.sh`, the first thing `scripts/deploy-phala.sh` runs, refuses a release while either placeholder remains: `gateway.Treasury` in `internal/gateway/payment.go` with its pin in `internal/gateway/pricing_test.go`, and the primary host in `rpcproxy/policy.yaml`. An attested identity or sales service with the placeholder treasury exits at startup, and so does the proxy with the placeholder host.
